## 3. 三個可能的根因

### A. design.md scope 太大 / 模糊
不太成立:
- design.md §3-§7 規範清楚,我每個 step 都讀 design 章節找 deliverables
- step 1.1-1.3 的 acceptance 都很具體(50-fetch wall time、boundary test、charter regression)
- codex 沒挑「設計缺陷」 — 只挑「實作對設計的覆蓋」

### B. codex 標準過嚴
**部分成立**:
- iter5 仍出 important 的「important」很多其實接近 minor(例如 step 1.3 iter5 #2 是「malformed port fallback 路徑」,正常輸入根本不會觸發)
- codex 對 marker / docstring / 命名 / 字串 hygiene 嚴格度高
- 但 iter5 也常挖到真實 bug(step 1.1 corrupt storage_state 不能 retry、step 1.3 contextmanager body 的 prohibition escape) — 這些不嚴

不是 codex 太嚴,是**codex 嚴格度匹配 production 標準**,我目前的 iter1 嚴格度低於它。

### C. 我的 iter1 實作節奏不夠保守
**最成立**:
- iter1 的 commit message 都寫得不錯,但**實作前的 threat-modelling 不夠**
- 例如 step 1.3:
  - iter1 沒想到 permit 一次性問題(雖然 docstring 寫了 idempotent 但沒 enforce)
  - iter1 沒想到 `inf` 會傳進 `time.sleep`
  - iter2 才修 userinfo,iter5 才修 contextmanager body
- 每個 step 我都把焦點放在「讓 acceptance test 過」,但沒系統性檢查「攻擊者輸入 / 失敗模式 / 並發 race / 命名衝突」
- iter 1 沒做 pre-flight checklist:
  - □ 攻擊者控制的字段如何流經我的 code?(URL / origin / robots body / port 數字)
  - □ 我的 callable 在 contextmanager / generator / property 中的執行時序?
  - □ 我的 mutable state 在多執行緒下的 race?
  - □ 我的例外有沒有 leak 原始輸入?
  - □ 我的 default 在 PRODUCTION mode 下會怎樣?
  - □ 我的 ports 有沒有對齊 production impl semantics?(noop vs real 的 API 對稱性)

## 4. 提議的方針(供用戶選擇)

### 選項 1:提高 reservation 上限到 8 並繼續
**理由**:
- 觀察 C 是真的,但 codex 嚴格度不會變,而剩 31 steps 至少還會累積 8-15 個類似 reservation
- 5/5 上限太低,系統性會在每 5 個 step 就觸發停損(已經是第二次 — 第一次是 prompt 0.3-1.2 5 個累計觸發)
- post-iter-5 fix-up 都有真實處理 finding,不是 swept under rug
- 這是 v2 的標準節奏,不是失敗

**代價**: 接受「85% 的 step 都會 DONE_WITH_RESERVATIONS」是 baseline

### 選項 2:強制 iter1 pre-flight checklist
**做法**:
- 每個 step 寫 test 之前先寫 `iter1-checklist.md`(只供本 session,不 commit):
  - 攻擊者控制字段表
  - contextmanager / property 執行時序表
  - 並發 race 表
  - 例外字串 sanitisation 表
  - PRODUCTION mode 行為表
  - noop / real impl semantics 對稱性表
- 這份 checklist 預防的議題在 iter1 commit 前全處理掉
- 預期效果:iter1 reject 數從 ~3 降到 ~1, iter5 reject 概率從 83% 降到 30%

**代價**:
- 每個 step 多 30-45 分鐘前置設計
- 可能仍會有 iter5 long tail(因為 codex 的搜尋寬度大於我的 checklist)

### 選項 3:選項 1 + 2 都做
**理由**: 同時提升上限(務實) + 改進方法(品質),平行收斂

**代價**: 上限放寬可能讓我變懶,但 checklist 應該抵消這風險

### 選項 4:暫停 v2 改走 V1 的 P1 follow-ups
不推薦 — design.md v2 是真的 v1 production gate 缺的 capability(rate limit / credentials / access control / LLM provider port v2 / PII)。逃避 v2 等於放棄 production gate。

### 選項 5:把 reservation 變成 P1 backlog item 而不是「失敗」
**做法**:
- 後續 step 完成 codex iter1-4,**不跑 iter5**
- iter4 還沒過的 important 直接列為 P1 backlog,step status = DONE
- 反正剩餘 important findings 大多會在 Phase 1 step 1.6 live tests / Phase 2 / Phase 6 整合測試浮現

**代價**:
- 風險變相轉嫁到 live tests,但 live tests 沒 codex 覆蓋
- 可能丟失 codex 在 iter5 才找到的真實安全議題(例如 step 1.3 的 contextmanager body)
