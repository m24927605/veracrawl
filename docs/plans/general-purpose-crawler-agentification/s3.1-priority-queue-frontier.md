## Why

- **Closes capability 2 / hint application gap.** s5+s6 record
  `decision.frontier_priority_hints` in the run report but the
  current FIFO frontier ignores them. s3.1 wires the consumer:
  pops items by `(-priority_score, enqueue_order)` where
  `priority_score = base + Σ matching_hint_deltas`. After s3.1,
  the hints actually steer the crawl.
- **Goal doc capability 1 completion.** s3 was narrowed during
  plan-review to "planned-seed ordering only"; s3.1 is the
  directly-dependent follow-up that makes hints binding.
- **AGENTS.md general-purpose constraint.** Hints work on any
  vertical (URL_PREFIX, HOST_GLOB, CONTENT_TYPE_PREFIX) — no per-site
  assumptions baked in.

## Scope

### In

- **New `PriorityCrawlFrontier` adapter** at
  `src/veracrawl/external_crawl/priority_frontier.py`. Same public
  interface as `ExternalCrawlFrontier` (enqueue / pop /
  mark_fetched / skip / budget_exhausted / counters / events) so
  the runner can switch between the two without other changes.
  Heap-based: `heapq` with `(-priority, enqueue_seq, FrontierItem)`
  tuples. Stable on priority ties via `enqueue_seq`.

- **`compute_item_priority(canonical_url, depth, hints)` helper**
  in the same module:
  - `base = 1.0 / (1.0 + depth)` (matches s1's seed decay so
    seed semantics carry over).
  - For each hint in `hints`: if the hint matches the URL/host
    per `match_kind`, add `hint.priority_delta` to the score.
  - Clamp to `[-2.0, 2.0]` (open question — see below).

- **Hint matching** (per `FrontierMatchKind`):
  - `URL_PREFIX`: `canonical_url.startswith(hint.match_value)`.
  - `HOST_GLOB`: glob-match `urlparse(canonical_url).hostname`
    against `hint.match_value` via `fnmatch.fnmatch`.
  - `CONTENT_TYPE_PREFIX`: not applied at enqueue time (we don't know
    MIME yet); recorded but no effect at this layer.

- **Ctor params**: ctor args mirror `ExternalCrawlFrontier`
  (no initial hints — they arrive via `add_hints` AFTER the
  planner runs).

- **`add_hints(new_hints: list[FrontierPriorityHint]) -> None`**
  method — called by the runner with `decision.frontier_priority_hints`
  after the initial plan AND with `decision_2.frontier_priority_hints`
  after each replan. Internally appends to the hint list,
  recomputes priority for every queued item, and `heapq.heapify`'s
  the heap. This is the mutable-hint interface that lets s6
  replan-derived hints actually steer subsequent enqueues.

- **Runner integration** — `ExternalCrawlRunner.__init__` gains
  one new opt-in ctor param: `frontier: FrontierLike | None = None`.
  When set, the runner uses it directly instead of constructing
  `ExternalCrawlFrontier`. Caller wires a `PriorityCrawlFrontier`
  pre-constructed (no hints yet). The runner then:
  1. After initial plan: calls
     `self._frontier.add_hints(decision.frontier_priority_hints)`.
  2. After each s6 replan: calls
     `self._frontier.add_hints(decision_2.frontier_priority_hints)`.
  Both call sites are guarded behind `hasattr(frontier, "add_hints")`
  so the legacy FIFO frontier (which doesn't implement it) is
  unaffected — no breaking change to s3/s6 callers.

- **Tests** (red list ≥ 20).

### Out

- **CONTENT_TYPE_PREFIX activation.** Recorded but not applied
  at enqueue time (we don't know content-type until fetch).
  Future slice when fetch-time MIME inspection lands.
- **Anti-starvation policies.** A `priority_delta = -2.0` URL
  could starve forever if higher-priority URLs keep arriving.
  Out of scope — caller's responsibility to bound hints.

## Design

### Module map

```
src/veracrawl/external_crawl/frontier_protocol.py         # new — ≤  40 LOC (FrontierLike Protocol)
src/veracrawl/external_crawl/priority_frontier.py         # new — ≤ 180 LOC
src/veracrawl/external_crawl/runner.py                    # modify — ≤  30 LOC (frontier= ctor arg + add_hints calls)
tests/unit/external_crawl/test_priority_frontier.py       # new — ≤ 380 LOC
tests/unit/external_crawl/test_runner_with_priority_frontier.py  # new — ≤ 180 LOC
tests/contract/test_priority_frontier_import_boundaries.py  # new — ≤  90 LOC
```

Behavior LOC: 40 + 180 + 30 = **250**. Under ≤ 300 cap.

### Cross-module flow

- `priority_frontier.py` imports stdlib (`heapq`, `fnmatch`,
  `urllib.parse`) + `veracrawl.contracts.crawl_planner.{FrontierPriorityHint}`
  + `veracrawl.contracts.enums.FrontierMatchKind`. No veracrawl
  adapter imports.
- Runner's new ctor arg is `frontier: FrontierLike | None`
  (direct injection of a pre-constructed frontier — NOT a
  factory). The runner does not import `PriorityCrawlFrontier`
  directly; the caller constructs it and hands it in. AST
  import-boundary test pins this.

### Replay invariant

- `enqueue_seq` is per-run-monotonic (0-indexed). Tie-break is
  deterministic: same URL order in → same pop order out.
- `compute_item_priority` is a pure function of (URL, depth,
  hints). No clock, no RNG. Replay-stable.

## Dependencies

- s1 (`FrontierPriorityHint` contract, `FrontierMatchKind` enum).
- s3 (runner already records `frontier_priority_hints` in
  `decision.frontier_priority_hints`).
- Existing `ExternalCrawlFrontier` interface (admission rules
  unchanged).

## Rollback

s3.1 only adds new behavior (new frontier class + opt-in
runner arg). Rollback is `git revert <s3.1-commit-range>` —
runner falls back to FIFO frontier (default unchanged).

## Open Questions

1. **Priority clamp range** (`[-2.0, 2.0]`): arbitrary. A
   future tuning slice may calibrate against corpus data.
2. **Heap mutation on replan**: when s6 replan adds new hints,
   `add_hints(...)` re-heapifies all queued items per their
   new priority. (Resolved — see §Scope; the previous
   "immutable" stance was iter-2's earlier design and is
   superseded by v2+.)
3. **`stable_hash`-based fallback ordering**: alternative to
   `enqueue_seq`. Default keeps enqueue_seq for explicit
   determinism.
